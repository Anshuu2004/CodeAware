# Implementation notes

A few things I worked out while building this that aren't obvious from reading the code. Mostly here so future-me doesn't have to relearn them.

## Why face-detection-adas and not a lighter detector

`face-detection-adas-0001` is the heaviest of the four models — most of the per-frame budget goes to it. I tried `face-detection-retail-0004` (smaller, designed for retail signage) early on. It's faster but the bbox jitters more between frames, which makes the downstream landmark regression jump around, which makes the eye crops jump around, which makes the eye-state classifier flip open/closed on alternate frames. The PERCLOS scorer eats some of that noise, but not all of it. The ADAS model was trained on dashcam-style imagery and produces stable boxes. Worth the extra few ms.

## Why the 35-point landmark model and not the 5-point one

The 5-point model gives you eye centres, not eye corners. To crop a square eye region you have to estimate scale from the inter-eye distance, which is brittle when the head turns. The 35-point model gives you four points around each eye, so you can take their bounding box and pad it. Robust to head roll, head turn, slight zoom changes — and only adds one tiny inference per frame.

## The async pattern in pipeline.py is not the textbook one

The textbook pattern enqueues frame N, then *immediately* starts preprocessing frame N+1, never blocking. Then a callback grabs results as they come in.

I tried that. It's correct on paper but it makes the visualisation lag by `jobs` frames (you see the bbox from the frame two ago superimposed on the current frame), and on a webcam at 30 FPS that lag is visible. The pattern in `pipeline.py` is a compromise: we still get preprocessing/inference overlap because the queue can run two requests in parallel internally, but each `process()` call returns the result for *that* frame. The downstream models (head pose, landmarks, eye state) then run sync on the face crop.

If you want to reproduce the textbook pattern, the right place to do it is inside `_process_async`. The comments there mark the spot.

## CPU plugin performance hint

```python
core.set_property(device, {"PERFORMANCE_HINT": "LATENCY"})
```

This tells the OpenVINO CPU plugin to optimise per-call latency rather than throughput. Without it the plugin defaults to a throughput hint that batches internally — great for a server, terrible for a 30 FPS webcam loop where every frame is a "batch of one". This single line accounts for ~10 FPS on my laptop.

## Why generate alert wavs at runtime instead of shipping them

I don't want to commit binary blobs into the repo. The wavs are generated by `alerts.ensure_alert_sounds()` on first run — a 440 Hz tone for drowsy, an 880 Hz tone for distraction, both 0.6 s with a small attack/release ramp. They sound fine. If you want fancier sounds, drop your own files at `assets/alert_drowsy.wav` and `assets/alert_distracted.wav` and the runtime will use yours.

## CSV is rising-edge only

Logging every frame where `is_drowsy=True` produces a 30 FPS firehose that nobody wants to read. The alerter only writes a row when the state transitions from "fine" to "alerted". The `duration_s` column on a distraction row is how long the head deviation had been sustained at the moment the alert fired (so almost always ~1.5 seconds, the sustain threshold).

## Things I chose not to build for v1

- A configurable cooldown per event type (right now both share the same 5 s cooldown).
- A "false alarm" feedback button so the driver can tell the system it was wrong.
- Per-driver calibration (some people naturally have a heavier eyelid; thresholds could shift).
- A web dashboard.

All of those are reasonable for v2. None of them are required for the demo.
